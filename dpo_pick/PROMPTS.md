## 1. terra: pairwise judge (decides the pair)

`gpt-6.1-terra`, Responses API, reasoning effort `low`, strict JSON. Prompt version **v1b.1** (the repository default is v1b; v1b.1 adds the sentence "Two valid artistic interpretations of the same request are similar." to the photo / illustration item, followed by a repeat of the sentence before it).

Each pair is called in both A/B orders; margin = P(B better) − P(A better) mapped to the same side and averaged; a pair is kept when the mean |margin| ≥ 0.8.

### developer message

```text
You compare two Markdown design briefs, A and B, written for the same user request. Each brief is the only input to an image generation pipeline: a layout model turns it into objects and text, then an image model renders it. The pipeline never sees the request. Decide which brief will produce the better final image, as judged by a person with good visual taste who also checks the image against the request.

What matters, roughly in this order:
1. Requirements kept: every explicit requirement of the request (subjects, counts, attributes, required text, exclusions, format) is present and unchanged.
2. Text on the image: the words to render are exactly right (wording, spelling, numbers, one language, no stray characters from another writing system), and the amount of text suits the format.
3. Coherence: no contradictions or physically impossible combinations; the main subject is described concretely and plausibly.
4. Design quality: a clear layout and focal point, and a fitting style, palette and composition; added details support the request.

Expanding the request is the brief's job: added composition, lighting, props and styling are good when they fit. Length, richness and amount of detail are never good or bad by themselves; do not prefer a brief for being shorter or longer.

Answer similar unless one brief will clearly give the better image. Small differences in wording, ordering or amount of detail are similar. Only pick a brief when you are confident that a careful viewer would agree.

# Avoid these wrong preferences
- Length: do not prefer the shorter brief. A longer brief is not more likely to fail just because it has more elements, more text or more detail; judge whether those additions are correct and fit the request. Before answering, ask yourself: if the two briefs were the same length, would I still pick the same one? If not, answer similar.
- Plainness: do not reward a brief for being plain, generic or safe. A richer composition with props, context and styling is better when it fits the request and keeps the requested subject in charge.
- Photos, paintings and illustrations with little or no text: most of the image quality comes from how the subject and scene are depicted. Prefer the brief whose main subject, pose, anatomy, materials, lighting and spatial arrangement are concrete, physically plausible and coherent. Differences in wording, ordering or optional props are similar. Two valid artistic interpretations of the same request are similar. Differences in wording, ordering or optional props are similar.
- Judge for a human viewer: do not favour a brief because it reads like a generic image-generation recipe (stacks of quality words such as cinematic, 8k, ultra-detailed, masterpiece). Concrete visual decisions matter; buzzwords do not.

# How to answer
First write reason in Simplified Chinese: at most 60 characters naming the difference that decides the answer (or why they are similar). Then give three probabilities that sum to 1: p_A_better, p_B_better, p_similar, meaning how likely a careful viewer comparing the two final images would say A is clearly better, B is clearly better, or neither. Use p_similar for everything you are not confident about.
```

## 2. luna: five pointwise checks (only ranks candidate pairs)

`gpt-6-luna`, Decisions API, ONE call per md with five choice questions. prior(md) = sum over the five checks of P(major); lower = cleaner. Candidate pairs = clean md vs the md with the largest prior gap; luna never decides or vetoes a pair.

### input

```text
You check ONE Markdown design brief written for a user's image request. The brief is the only input to an image pipeline that draws exactly what the brief says; the pipeline never sees the request. Answer each question on its own: each looks for one kind of clear mistake only and ignores every other quality of the brief. Most briefs are fine: answer none unless the mistake is really there and you can point to it.

# User request
<request>
Target aspect ratio: <aspect ratio>

# Brief
<md>
```

### questions (name: instructions); every question has the same three choices

**text**

```text
Required text copied wrongly. First find the text the request asks to appear in the image: quoted strings, titles, headings, labels, names, slogans, numbers, prices, dates. If the request asks for no specific text, answer none. Otherwise compare each required string, character by character, with the text the brief tells the pipeline to print. Count as a mistake: a misspelled, re-worded, translated, transliterated or truncated string; a changed letter case where the request is explicit; changed digits, units or symbols (such as ™, &, %, currency signs); punctuation added or dropped (a period or comma from the request's own sentence printed after a short title, label or name: the request 'a sign that says "OPEN 24 HOURS".' asks for OPEN 24 HOURS; but '!' or '?' inside a slogan, 'CO., LTD.' and the period of a quoted full sentence belong to the text); a required string missing, printed twice, or split across places. A large unrequested headline that competes with the required text is minor. Major = a viewer would read a wrong or missing required string.
```

**ending**

```text
The brief does not end properly. Count as a mistake: the brief stops in the middle of a sentence, list or section, or a section it announces is missing; the same sentence, list item or phrase is repeated over and over; the brief contains self-correction or working notes instead of a clean description (for example '-> wait', 'no, exact copy:', 'X is not used; the exact lettering reads Y', 'corrected to', 'let me fix'), or other leftover reasoning, meta comments or garbage characters. A brief that is short but complete and clean is NOT a mistake here. Major = the pipeline would draw garbled, duplicated or missing parts because of it.
```

**short**

```text
Too thin for the request: information the image needs is lost. Look at what the request explicitly asks for (items, people, objects, panels, sections, rows, data points, steps, text blocks, details of the subject, setting, style). Count as a mistake: requested content dropped; several requested items merged or summarised into a vague phrase ('various icons', 'some text', 'dates 1 to 31') instead of being specified; a long or detailed request answered with a brief so short that the layout, arrangement or look of the main subject is left to guesswork. Extra detail the request did not ask for is NOT needed; do not count a concise brief that still covers everything requested. Major = a viewer comparing the image with the request would notice missing or vague content.
```

**aesth**

```text
A clear aesthetic mistake the brief commits the image to. Count as a mistake: so many elements or text blocks that the image will be cluttered or cramped; important text that will be too small, low contrast or placed over a busy background; a palette or style mix that clashes with itself or the request's mood; no clear focal point or hierarchy; the main subject awkwardly cropped, tiny, or off balance for the aspect ratio; a design that will look cheap, generic or amateurish for its purpose (a poster, cover, menu, slide, logo). Do NOT count a style simply because you would choose another one; only count choices that would make most viewers find the image worse. Major = most viewers would find the image clearly unattractive or hard to read because of it.
```

**align**

```text
Inconsistent with the request. Count as a mistake: the brief changes what the request asks for: a different main subject, entity, character, brand or setting; a different medium or style (a photo when an illustration is asked, or the reverse); a wrong count, size, position, relation, color or action the request states; a different format or layout (a poster asked, a scene given; a grid of 4 asked, 6 given); a required element missing; an unrequested element that takes over the image; or two parts of the brief that contradict each other. Reasonable additions that serve the request are NOT mistakes, and do not judge text spelling here. Major = a viewer comparing the image with the request would say it does not show what was asked.
```

## 3. Hard rule (no model)

An md is a hard negative (never chosen, tried first as rejected) when it is not format-valid, did not finish (`finish_reason != stop`), or matches:

```regex
->\s*wait|\bwait,? no\b|exact copy:|is not used;|is omitted;|corrected to exact|let me (fix|correct)
```
(case-insensitive)
